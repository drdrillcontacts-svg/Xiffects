# بررسی واقعی سورس Xiffects

این بررسی روی فایل‌های فعلی workspace انجام شد. کد صوتی، رابط، پارامترها و Build تغییر نکردند؛ فقط این گزارش و خروجی خام اجرای مجدد تست ثبت شدند. تغییرات موجود از مراحل قبلی باقی مانده‌اند؛ بنابراین ثبت Reference باید محتوای فعلی فایل‌های tracked و untracked را پوشش دهد، نه فقط شناسهٔ HEAD.

## ۱. معماری موجود

- **زبان و ابزار:** C++17، JUCE 8.0.6، CMake و CTest؛ گردش‌کار GitHub Actions با YAML. موتور و رابط، HTML/WebView یا سرویس پردازش ابری نیستند.
- **میزبان/پارامترها:** `Source/PluginProcessor.{h,cpp}` شامل AudioProcessor، APVTS، تعریف پارامترها، آماده‌سازی، مسیریابی، اتومیشن و ذخیرهٔ state است.
- **DSP مستقل از JUCE:** `Source/DSP/Effects.h` و `Source/DSP/Pitch.h`؛ اما ترکیب کامل موتور هنوز داخل AudioProcessor است.
- **رابط:** `Source/PluginEditor.{h,cpp}` و `Source/UI/Controls.h`؛ مؤلفه‌های واقعی JUCE با attachment. تصویر hero فقط asset است.
- **انتقال دادهٔ نمایش:** `Source/Telemetry.h` یک صف محدود SPSC با atomic دارد؛ صف پُر، دادهٔ نمایش جدید را رها می‌کند و منتظر GUI نمی‌ماند.

### مسیر واقعی صوت

ورودی → اصلاح کوک → Octaver و Pitch Shifter موازی → Compressor → Distortion → EQ → Phaser → Delay → Reverb → Output gain و محدودسازی سخت ±1.

POWER خروجی را با مسیر dry تأخیردار ترکیب می‌کند؛ خاموش‌کردن افکت‌ها به معنی حذف محاسبات یا حذف بافرهای pitch نیست. مرجع: `PluginProcessor.cpp:108–163`.

### Auto-Tune واقعاً چه می‌کند؟

در `DSP/Pitch.h`، YIN پس از low-pass و کاهش نرخ تحلیل، روی پنجرهٔ ۵۱۲ نمونه با hop برابر ۱۲۸ نمونه کار می‌کند. محدودهٔ انتشار Pitch برابر 100–1600 Hz است. کانال چپ/مونو ورودی تحلیل می‌شود.

`PitchCorrection::process` نت هدف را از اشتراک گام و کلیدهای دستی پیدا می‌کند؛ hysteresis برابر ۱۵ سنت، Strength، هموارسازی Retune و تبدیل اختلاف به نسبت فرکانس وجود دارند. محاسبات هدف و ضریب ثابت cache می‌شوند. `PitchShifter::process` صدا را با دو read-head پنجره‌دار تغییر می‌دهد؛ بنابراین اصلاح کوک صرفاً نمایش نیست.

این پیاده‌سازی formant preservation، مدل مخصوص آواز، حالت Live مستقل یا آزمون تأییدشده روی ضبط واقعی آواز/ساکسوفون ندارد.

### Buffer و پارامترها

`prepareToPlay` بافرهای pitch، delay، reverb و dry bypass را تخصیص/ریست می‌کند و تأخیر اسمی را به میزبان می‌دهد. حلقهٔ نمونه، بافرهای موجود را می‌خواند/می‌نویسد؛ در مسیر بررسی‌شده I/O، mutex یا تخصیص صریح حافظه دیده نشد. مونو/استریو با ورودی و خروجی هم‌اندازه پذیرفته می‌شوند.

پارامترها در شروع هر بلوک خوانده می‌شوند و مقادیر پیوسته در هر نمونه هموار می‌شوند؛ این را نباید با پشتیبانی کامل از رویداد اتومیشن دارای sample-offset اشتباه گرفت. پردازش کامل به اجرای قبلی prepare و layout معتبر میزبان متکی است.

## ۳. مشکلات قابل استناد و محدودیت شواهد

1. **مراحل تأخیردار همیشه در مسیر هستند:** `PitchShifter::latency` و `prepareToPlay` و پردازش بدون شرط شِیفترها. هدف Live با حفظ همین تأخیر قابل دستیابی نیست؛ امکان‌پذیری روش جایگزین هنوز آزمایش نشده است.
2. **عدم هم‌زمانی sidechain کمپرسور:** peak ورودی در خط ۱۲۶ گرفته می‌شود، اما gain در خطوط ۱۳۷–۱۳۸ روی صدای بعد از pitch اعمال می‌شود. این رابطهٔ زمانی قطعی است؛ میزان اثر شنیداری آن هنوز اندازه‌گیری نشده است.
3. **presetهای غیرپیش‌فرض snapshot کامل نیستند:** `PluginEditor.cpp:54–82` فقط بخشی از پارامترها را تنظیم می‌کند. در نتیجه تنظیمات پیشین می‌توانند باقی بمانند.
4. **بارگذاری preset اتمیک نیست:** `choosePresetFile` پارامترها را یکی‌یکی اعمال می‌کند. اعتبارسنجی تعداد کامل شناسه‌ها، تکرار شناسه و schema version ندارد؛ خطر مشاهدهٔ وضعیت میانی در صوت وجود دارد، نه اثبات رخ‌دادن کلیک.
5. **اعتبارسنجی فایل و state یکسان نیست:** loader رابط بررسی‌هایی دارد، ولی `setStateInformation` در خطوط ۱۷۸–۱۸۲ پس از بررسی root tag، state را جایگزین می‌کند.
6. **محاسبهٔ متمرکز YIN:** `analyse` تمام lagها را در یک فراخوانی محاسبه می‌کند؛ آزمون کوتاه بدون deadline miss تضمین اجرای زنده نیست.
7. **کیفیت الگوریتم‌ها محدود است:** ریورب comb-bank، EQ یک‌قطبی و سقف خروجی hard clamp هستند؛ سقف خروجی یک limiter شفاف نیست. گرانول‌های pitch نیز read-position متغیر دارند.
8. **پوشش تست با محصول کامل یکسان نیست:** `RealtimeTests.cpp` زنجیره‌ای مستقل با یک شِیفتر می‌سازد، نه اجرای کامل `processBlock`. تست allocation همهٔ انواع تخصیص یا رفتار میزبان را پوشش نمی‌دهد. `Tools/PitchProfile.cpp` نیز مسیر کامل نهایی را رندر نمی‌کند. تست طیفی فعلی نزدیک فرکانس موردانتظار جست‌وجو می‌کند و ممکن است خطای غالب دورتر را نبیند.
9. **محدودهٔ Pitch برای همهٔ آوازها کافی نیست:** خروجی زیر 100 Hz پشتیبانی‌شده فرض نشده است. آزمون‌های مصنوعی موجود جای آزمون جداگانهٔ آواز و ساکسوفون نیستند.

## ۴. اجرای مجدد در همین بررسی

- CMake Release و چهار CTest موجود: **۴ از ۴ موفق**؛ DSP، Pitch، CorrectionRegression، Realtime.
- ابزار موجود PitchProfile اجرا شد؛ خروجی خام در `docs/measurements/source-review-current.csv` است.
- مثال صرفاً نرم‌افزاری: در 48 kHz آزمون impulse دو شِیفتر unity، ۲۸۸۴ نمونه فاصله نشان داد. این اندازه‌گیری واحدهای نرم‌افزاری است، **نه تأخیر واقعی ورودی تا خروجی محصول**.
- همان ابزار برای سینوس‌های آزمایش‌شده در 48 kHz، اولین تشخیص معتبر را پس از ۲۰۴۸ نمونه نشان داد. این «زمان کسب تشخیص» است، نه transit delay.
- اجرای کوتاه ابزار در بافرهای 32/64/128/256 از deadline تعریف‌شدهٔ خودش عبور نکرد؛ این نتیجه فقط دربارهٔ همان workload مصنوعی زیرسیستم Pitch است.
- پیکربندی native دوباره امتحان شد و در `Could NOT find PkgConfig` متوقف شد. در این نوبت پنجرهٔ واقعی، HostTests، VST3 در DAW یا تست سخت‌افزار اجرا نشده‌اند. بیلدهای تاریخی Windows را به نسخهٔ جاری تعمیم نمی‌دهیم.
- **هیچ تأخیر سخت‌افزاری/واقعی محصول، کیفیت ضبط زنده یا آمادگی تجاری تأیید نشده است.** اهداف ۱۰/۱۵ ms همچنان اهداف بررسی‌نشده‌اند.

## ۵. روش واقعی Build VST3

`CMakeLists.txt` با FetchContent نسخهٔ JUCE را دریافت می‌کند؛ `juce_add_plugin` خروجی‌های VST3 و Standalone می‌سازد و تصویر را با BinaryData جاسازی می‌کند. workflow ویندوز configure، build، CTest و سپس upload-artifact دارد. وجود workflow به معنی اجرای موفق جدید نیست.

در Developer PowerShell ویندوز دارای Visual Studio 2022 Desktop C++:

```powershell
cmake -S . -B build-reference -A x64
cmake --build build-reference --config Release --parallel 2
ctest --test-dir build-reference -C Release --output-on-failure
```

خروجی VST3: `build-reference/Xiffects_artefacts/Release/VST3/`.

## ۶. تغییرات مرحلهٔ بعد؛ هنوز اعمال نشده‌اند

| فایل | تغییر پیشنهادی |
|---|---|
| `Tools/ReferenceRender.cpp` — جدید | رندر ورودی یکسان از **processor واقعی**؛ جلوگیری از متفاوت‌شدن زنجیرهٔ آزمایش با محصول |
| `Tests/ReferenceTests.cpp` — جدید | برابری رندر در بلوک‌بندی‌های مختلف، state، bypass و دادهٔ خروجی |
| `Tests/HostTests.cpp` | پوشش مسیر فعال صوتی، نه فقط POWER-off و smoke test رابط |
| `Tools/PitchProfile.cpp` | برچسب‌گذاری دامنهٔ اندازه‌گیری و افزودن مقایسه/معیارهای گسترده‌تر؛ حفظ نتایج قدیمی |
| `CMakeLists.txt` و workflow | target آزمایشی اختیاری، Windows reference tests و آرشیو نتایج |
| `docs/reference/` — جدید | manifest فایل/تنظیمات، hashها، مشخصات build و گزارش مقایسه |

در مرحلهٔ ثبت Reference، فایل‌های `Source/DSP/*`، `PluginProcessor.*` و `PluginEditor.*` تغییر نمی‌کنند. موتور Live بعداً جدا و پشت انتخاب آزمایشی اضافه می‌شود؛ طرح استخراج موتور مشترک هم پس از داشتن regression مرجع اجرا خواهد شد.

## ۷. ترتیب دقیق اجرای تست مرحلهٔ بعد

1. ثبت hash سورس فعلی، تنظیمات کامل، نسخهٔ compiler/JUCE و build flags؛ فقط HEAD برای این workspace کافی نیست.
2. بیلد تازهٔ Windows Release و اجرای همهٔ CTestها؛ نگهداری گزارش و باینری مرجع.
3. اعتبارسنجی VST3 با pluginval و آزمون در نسخهٔ ثبت‌شدهٔ REAPER.
4. رندر از processor واقعی با fixtureهای deterministic در 44.1/48/96 kHz، بافرهای 32/64/128/256/512 و بلوک‌های متغیر/خالی؛ بررسی صوت، state و اتومیشن.
5. ساخت مجموعه‌های جداگانهٔ آواز و ساکسوفون با ضبط خشک دارای مجوز و annotation مناسب؛ در نبود فایل، وضعیت «انجام‌نشده» بماند.
6. ثبت خروجی Reference، سپس ساخت نمونهٔ جداگانهٔ Live؛ مقایسه با همان ورودی/تنظیمات، تحلیل طیفی گسترده، خطای اکتاو، onset/settling و زمان بلوک.
7. تست loopback روی Windows/ASIO با ثبت دستگاه، درایور، DAW، نرخ و بافر؛ فقط این مرحله مبنای عدد ورودی تا خروجی سخت‌افزاری است.
8. آزمون طولانی و شنیداری جداگانه برای هر دو گروه؛ تصمیم دربارهٔ پذیرش Live فقط پس از نتایج. Reference حذف نمی‌شود.
